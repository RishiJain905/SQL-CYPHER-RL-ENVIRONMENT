RThe review: what held, what changed

The finding behind most of the changes: the trainer's forward pass under-reads a small LoRA, by about half at the pilots' size. Each adapted layer's output is rounded to bf16 after the LoRA's small addition, so part of it is rounded away. The rollout server applies all of it. The pilots' rollouts and scores were right; their logged KL was too low, and the "growing gap" between server and trainer was this effect.

01The environment

R5's rule: what the model reads, and what decides its reward, must match deployment; the plumbing behind it may be artificial. In run 1 the model never sees what its query returns, so the environment is just two things: the prompt and the reward.

Must match deploymentMay be artificial
The prompt: chat template, system prompt, how the schema is writtenWhere the databases run (containers, local files)
The tool's call formatIsolation: read-only, no network, reset after each episode
Real database engines (the real errors)Timeouts and concurrency sized for training
Realistic data wherever the model looks (run 2)Live system or frozen snapshot

What the model reads

  • The prompt: the tool-call prompt SFT trained on, which the pilots and the yardstick already use (schema, up to two tested examples, the question), rendered with the release's chat template by llama-server itself.
  • To check before release: the model card shows this exact system prompt and tool schema, so people who run the model send what it was trained on.
  • What samples the answers: the SFT weights with the LoRA merged in, quantised to Q8_0. That is the model that would ship.
  • Thinking level: high everywhere, as in the pilots and the yardstick. Mixing levels would make the model robust to a user's choice, but would change what the yardstick measures.
  • Thinking budget: 1,024 tokens, then a forced </think> that carries no loss (4–16% of the pilots' answers hit it).

What decides the reward

  • Checker 4, imported unchanged. 1 right, 0 wrong, −0.1 for no parsable call; an undecided answer is left out of its group and the loss.
  • A floor under the group's standard deviation (0.25), so a small reward difference never becomes a full-size advantage.
  • Every question is used once. The checker's databases use fixed seeds, so a question seen often could be answered for those copies only.
  • Questions that can't teach are left out: each reference query is scored by the checker as if the model had written it. One the checker can't decide (it returns nothing, or only zeros and NULLs) would make every rollout "undecided".
  • Canaries every step: share of queries using DISTINCT, using SELECT *, replies with several calls, thoughts that cite a "correct solution" (the teacher leak). Plus reading the top-reward samples at each evaluation.

Infrastructure: llama-server on Windows started by run 1 itself, one WSL process per update, the checker's Neo4j in Docker (the update refuses to run without it), and the pause switch (tested mid-rollout).

02The questions

From the pilots: 38–63% of groups carried a signal (about half on average). The rest were all right or all wrong and cost rollout time only.

  • A fresh pool-v2 from the training split, with the filters above; evalset and test questions excluded by id and text, prompts of at most 4,000 tokens. Enough questions for 200 steps.
  • No probe pass. Probing 2,000 questions × 8 samples would take about as long as the rollout time it saves over 100 steps. Groups with no signal are skipped, and the informative share is logged.
  • The mix of 32 per step is a real choice. CypherBench has the most room but trains on 4 graphs and is measured on 7 others; text2cypher has the weakest reward (random graphs, half its questions undecidable). Your call

03The method

SRPO, as piloted (R4): routed per rollout, an EMA teacher at 0.05, the right sibling's query as the correct solution, top-100 JSD, entropy weights, token-mean loss. It led on every sampled measure; none of it was outside noise.

Two caveats the draft left out. The pilots compared two whole recipes (SRPO's against Dr. GRPO's, whose gradient is ~12× smaller by construction), not the distillation alone. And SRPO gives the "never" questions no direct signal: distillation needs a right sibling. What it adds is a token-by-token target for the wrong answers of mixed groups.

The gap's cause was found before the build: with the pilot's LoRA applied at twice its strength, the trainer's log-probs match the server's again (0.016 a token, close to the 0.013 of no LoRA at all). The gradients are not affected, and the effect fades as the LoRA grows.

04Length, evaluations and the gate

  • 100 steps first, about 18 GPU hours plus pauses, evaluated after steps 25, 50 and 100 on step 1's yardstick (evalset, temperature 1.0, 8 samples, checker 4, plus greedy), served from the merged model.
  • Extend to 200 only if mean@8 is still rising at 100 and the gate holds; 300 stays the ceiling. Your call
  • The gate: pass@8 not down, question by question: questions that lost their last right answer against questions that gained a first one. More lost than gained with p < 0.05 pauses the run and keeps the last good adapter.
  • The test set is used once, on the adapter we keep.

06Where the code is

Run 1 is self-contained: src/sqlrl/run1/, scripts/run1/, tests/run1/, documentation/run1/, its runs under <data>/run1/. It imports nothing from the pilots and the pilots import nothing from it; the piloted loss code is copied, and tests prove the copies give the pilots' numbers. Shared: only the yardstick (step 1's sampler and scorer) and the paths.

Built: the pool builder, the server launcher, the rollout scheduler, the update with its probe, the merge into the GGUF, the canaries and stop rules, the run loop with evaluations and the gate, pause. 20 CPU tests; two loop tests end to end (2 steps of SQL questions); pause and resume tested mid-rollout.

Not yet run: the pool build and an evaluation end to end. Both need the checker's Neo4j, and Docker's engine would not start during the build session.

07Decisions for Rishi

1 · The dataset mix of each step's 32 questions

Recommended10 CypherBench · 10 gretel · 8 SQaLe · 4 text2cypher (decidable only): compute where the room and the cleanest reward are.
AlternativeThe pilots' even 8 per dataset: simplest, directly comparable with the pilots.

2 · The learning rate

Recommended1e-5 with 5 warm-up steps; raise it only if step 25 shows no movement.
Alternative2e-5 from the start. The review found no case for it: the real policy already moved more than the pilots' logs showed.

3 · The length

Recommended100 steps (~18 GPU hours), then decide on 200 from the evaluations.
AlternativeA fixed number now (200 or 300), with the same gate and stop rules.

Built with the recommended value of each

The three choices above are arguments of the start command (--mix, --lr, --steps), so another value needs no code change. Everything else is as the review settled it.
