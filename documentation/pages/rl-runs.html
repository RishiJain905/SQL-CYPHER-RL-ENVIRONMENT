The Two RL Runs

Run 1 trains the agent on the task as it is today: one query per question. Run 2 trains it as a real agent, one that sees what its query returned and can try again. This page lays out both as planned, the ways they could be structured instead, the methods on the table, and the decisions still open.

In short. Run 1 is the task as it is today: the model writes one query, an execution check scores it, and RL pushes it toward the answers that checked out. Run 2 is the task as a real agent has it: the model sees what its query returned, may look around or retry for 3-4 turns, and is scored on the final query.

The baseline says run 1 has room (greedy 43.2% against pass@8 62.6%) and where it doesn't (74 of 198 questions are never right in 8 tries). It says little about run 2, because the baseline is single-turn.

This is not a decision document. Where the plan is silent the page says so, and paper claims were checked against the arXiv pages. What could not be read is marked.

Where we start

The released model (step 1,500 of the SFT run, merged, Q8_0) answered each of the 200 evalset questions 8 times at temperature 1.0. 198 questions had at least one answer the checker could decide.

How the 879 wrong answers fail
613 ran and returned different rows, 194 errored at run time, 48 didn't parse. About a quarter are errors that a retry could see.
Noise
Eight single-sample runs of the unchanged model scored 36.0% to 43.0%. One rate on 200 questions is good to about ±3.5 points. Temperature 1.0 costs 6.3 points against greedy, and 96.5-98.0% of answers are still well-formed calls.
Test set
On the 1,000-question test set the model scores 43.7%, against 32.5% for the base model.

The two runs as planned

Both runs train a new LoRA on the merged SFT model, so the KL reference is the same model with the adapter switched off and SFT stays intact. Rollouts come from llama-server (Q8_0 plus the adapter as a GGUF LoRA); training is bf16 PEFT. Only training-split questions are used. The evalset and the test set never reach a rollout, a reward or a filter.

Run 1: single turn, execution reward

stage A
The task
Unchanged. The model thinks (budget 1,024 tokens), writes one query, and never learns what it returned.
Checker 4
SQL runs on gretel's real rows and on randomly filled copies (plus near-miss and rescue copies). Cypher runs on CypherBench's sampled graphs, or on random graphs built from the schema for text2cypher. Rows compare as multisets, column order is free, and ties at a final LIMIT count neither way. Answers no copy can decide are undecided.
Which questions

The plan says the ones the model sometimes gets right. Two things it leaves open.

The model saw these training questions in SFT with their reference queries, so the training split's "sometimes" pool probably differs from the evalset's. That is my inference; a probe of a few hundred training questions would show it.

And 300 steps × 32 questions visits about 9,600 of a ~95,000-question pool, so which ones is a real choice.

What it can move

pass@1 can climb toward pass@8, not far past it. RL mostly reweights what the model can already produce: Yue et al. (2025) found RL-trained models gain at small k and lose to their base models at large k.

Closing a quarter of the 19.4-point gap is about +5 points, half about +10. That is scale, not a forecast. The pass@8 ceilings: CypherBench and gretel 80.0%, SQaLe 57.1%, text2cypher 32.7%.

The catch on CypherBench
Its training questions cover 4 graphs (art, biology, soccer, terrorist_attack). The evalset's cover 7 others, so the +35 points are measured on graphs RL never saw.
Out of reach
The 74 "never" questions are out of reach of a group-comparison method. text2cypher's 33 are mostly unverifiable or hopeless on random graphs.
Done looks like
A step budget or a plateau, then step 1's measurement. Pass means pass@1 up, pass@8 not down, canaries steady.

Run 2: multi-turn agent in real databases

stage B
What changes

The observation step. SFT never showed the model a tool result, so early trajectories are new territory. The release card lists this as a limitation. SFT answers sometimes spend their one query looking around (SELECT DISTINCT home_type FROM ...), which a single-turn score marks wrong. A smoke run on the base model put exploration at about 8% of failures (11% on gretel).

Tool output is context, masked from the loss, as in Search-R1 ("retrieved token masking").

Why the databases matter
gretel's rows and CypherBench's sampled graphs are real, so seeing them tells the model something. SQaLe's and text2cypher's checker databases are random fills built from the schema; looking at them teaches little about the question's real values. The plan doesn't say how those two get real data. SQaLe's populated databases exist upstream but weren't downloaded.
What it can move

A retry is an extra attempt, so run 2 isn't capped by single-turn pass@8. The clean win is the ~27% of failures that are errors or parse failures. The 70% that ran and returned different rows are harder: rows reveal a wrong filter only if the result is empty, absurd or the wrong shape.

Published multi-turn SQL RL reports gains from small data: SkyRL-SQL (7B, ~600 training examples, up to +9.2 points on five Spider benchmarks; I couldn't open its blog for the reward details) and MTIR-SQL (a 4B model, 64.4% on BIRD dev, GRPO modified, KL dropped). Expect gains to concentrate on gretel and CypherBench.

Not settled in the plan
How the model ends (a plain reply, or a submit tool). Which call is the answer (the last, presumably). Per-turn thinking budget. Row cap. Query timeout: the checker's Neo4j allows 20 s, too long when a slot waits on it. Context length: SFT trained at a 4,096-token maximum, and four turns with up to 1,024 thinking tokens each can exceed that.
Done looks like
A step budget or plateau, then two measurements: a multi-turn score against a multi-turn baseline of the released model (which doesn't exist yet), and the old single-turn score, to show nothing was unlearned.

A claim in the plan to check

The plan says a first-try right answer "is still the best outcome, so it doesn't unlearn stage A". With a reward on the final query only, a first-try success and a third-try success pay the same. The claim holds only with some pressure for early answers (see alternatives, E).

The measurement and the gate

Same questions and settings (temperature 1.0, 8 samples, checker 4) on the released model, each pilot, after each run, and on the final model. The test set only confirms a finished stage.

What the gate can see
On 198 questions a sign test needs about 15 questions changed to right against 5 changed to wrong (p ≈ 0.04): a net swing of 10, about 5 points. Pilots will often differ by less. Per-question mean right-rates over all ~1,450 decided samples are more sensitive than greedy.
pass@8 is a ceiling
It is the ceiling at 8 tries. An RL model can improve at 8 and look unchanged at 64.

Alternatives worth discussing

Ways to structure the two runs, with honest pros and cons. The recommendation at the end is mine, not the plan's.

ARun 2 only, multi-turn from the start

ProOne run. Single-turn is the special case of answering on turn 1. Multi-turn SQL RL is published as a direct recipe.

ConThe cold start meets a model that has never seen a tool result, with no single-turn gain banked and costlier steps. It loses the cheap, clean run-1 check that the pipeline works.

BInterleave single- and multi-turn

Each batch mixes max_turns=1 and max_turns=4 questions, or lets the model stop after turn 1.

ProOne adapter, no handover, single-turn skill keeps being rewarded.

ConMore moving parts, uneven step times, harder attribution.

CPer-dataset curricula

E.g. CypherBench first (biggest gap, cleanest reward), gretel for real rows, SQaLe and text2cypher later or only in run 1.

ProCompute goes where there is room and a trustworthy reward.

ConCan overfit one dataset's habits (CypherBench is template-like, on 4 graphs).

DRun 1 as a short warm-up

The pilots are stage-A runs: continue the winner briefly and put the budget into run 2.

ProNo repeated work. Run 1's gains are capped by pass@8 anyway.

ConGives up the large single-turn gap (CypherBench +35) if run 2 can't exploit it.

EReward shapes for run 2

  • Final query only (the plan). Simplest, nothing to game, but no pull toward early answers.
  • Per-turn cost (say reward × 0.9 per extra turn). Makes first-try best, as the plan intends; too large and the model stops looking. A first-try bonus does the same and is easier to log.
  • A small score for a query that runs. Arctic-Text2SQL-R1 paid 1 for a match, 0.1 for valid executable SQL, 0 otherwise, and reports that finer-grained rewards produced "lazy" behaviour. The plan's malformed-call penalty is close to this.

FA cold start for run 2

One round of rejection-sampling fine-tuning first: run the model as a multi-turn agent, keep trajectories that end right, train on them (as the trace stage did for thinking).

ProThe model learns the observation format before RL spends rollouts on it.

ConAnother stage and dataset to keep off the evalset.

GDifferent methods per run

A GRPO-family method for run 1; SDPO or SRPO in run 2, where their feedback is natural (see the methods).

ConChanges the method and the task at once.

Recommendation (mine, not the plan's)

Keep two runs, overlapped. (1) Treat the pilots as the first slice of run 1 and continue the winner. (2) Measure the released model as a multi-turn agent before building run 2's trainer: it shows how much of the error-type failures a retry fixes with no training. (3) In run 2, mix single- and multi-turn episodes with a small per-turn cost, and give it observations only where the data is real (gretel, CypherBench). (4) Add a rejection-sampling cold start only if the zero-shot multi-turn run is clearly broken.

The methods

For a question, sample G answers o₁..o_G from the policy and score them with the checker for rewards r_i (0 or 1). π_θ is the policy being trained, π_old the one that produced the samples, π_ref the SFT model with the adapter off.

Why not the classics

PPO needs a critic, a value network about the policy's size, which doesn't fit next to a 4B model on 16 GB. DeepSeekMath drops it for the same reason, and Arctic-Text2SQL-R1 found GRPO ahead of PPO (64.9 vs 63.0 BIRD dev, with the caveat that PPO may need more tuning). RLHF with a learned reward model is unneeded when the checker verifies answers. DPO (offline preference pairs) could be built from right and wrong samples with no rollouts in the loop, but isn't on-policy and uses the checker's signal indirectly. A cheap control is rejection sampling (train on the right samples); it isn't in the pilot list.

GRPO

DeepSeekMath, 2024 · the safe default

No critic: the baseline is the group's own average. An answer is good when it beats its siblings. A group that is all right or all wrong has zero advantage and teaches nothing.

A_i  = (r_i − mean(r)) / std(r)       same for every token of answer i
loss = −(1/G) Σ_i (1/|o_i|) Σ_t min(ρ_it·A_i, clip(ρ_it, 1−ε, 1+ε)·A_i)
       + β · KL(π_θ ‖ π_ref)

ρ is the per-token ratio π_θ/π_old. The paper used β = 0.04, with the KL in the loss. Suits run 1 directly.

Dr. GRPO

Liu et al., 2025 · removes two biases

It removes two terms GRPO added. The 1/|o_i| makes long wrong answers cost less per token, so they drift longer. The division by std gives questions with nearly all-right or all-wrong groups bigger weights.

A_i = r_i − mean(r)        sum divided by a constant (e.g. the token budget)

DAPO

Yu et al., 2025 · four changes and no KL
  • Clip-higher. ε_low 0.2, ε_high 0.28, so unlikely tokens can rise and entropy doesn't collapse.
  • Dynamic sampling. Drop all-right and all-wrong groups; keep sampling until the batch is informative.
  • Token-level loss. Divide by the batch's tokens, not per answer.
  • Overlong shaping. A soft length penalty near the cap.

It also drops the KL term. On a 32B math model the ablation climbs from 30 (naive GRPO) to 50 on AIME 2024. Dynamic sampling matters most here: rollouts go only where there is a gradient.

GSPO

Zheng et al., Qwen, 2025 · one ratio per answer
s_i = ( π_θ(o_i | q) / π_old(o_i | q) ) ^ (1/|o_i|)     clipped at a tiny ε
                                                        (3e-4 / 4e-4 in their MoE runs)

The argument: the reward belongs to the sequence, and per-token ratios, each from one sample, add noise that accumulates. It is also more tolerant of small likelihood differences between the rollout engine and the trainer, which matters here (see the RL facts).

SDPO

Hübotter et al., ICML 2026 · arXiv title "Reinforcement Learning via Self-Distillation"

GRPO's signal is one number per answer. SDPO uses the text the environment returns (an error, a failed test). The same model, shown that feedback in its prompt, becomes a self-teacher, and the policy (without the feedback) is pulled toward the teacher's token predictions.

loss = Σ_t KL( π_θ(· | q, o_<t)  ‖  stopgrad π_θ(· | q, feedback, o_<t) )

The teacher's prompt holds the question, the feedback and, if one exists, a correct answer from the same group. Credit is dense: tokens the teacher likes more than the student get pushed up.

In the paper (Qwen3-8B, 8 rollouts, temperature 1.0): 48.8% vs 41.2% for GRPO on LiveCodeBench v6, reaching GRPO's final accuracy in 4× fewer generations, and answers ~3× shorter on its science tasks. The implementation uses a Jensen-Shannon divergence and an EMA or trust-region teacher for stability, plus an extra forward pass.

Caveats from the paper: it needs a model strong enough to use in-context feedback (it lost to GRPO on a 1.5B model); misleading feedback hurts; and agentic and long-horizon use is listed as untested. For us the question is what counts as feedback. The model's own error or rows, plus a correct sibling, are fair. The reference's rows would leak an answer the deployed model never sees.

SRPO

Li et al., 2026 · routes samples between GRPO and SDPO

The authors say SDPO learns fast, then often collapses in long training, and blame two things: distilling on answers that were already right is ambiguous, and the self-teacher gets less reliable over time. SRPO routes each sample. Right ones go to GRPO's reward update, failed ones to SDPO's correction, with distillation targets weighted down when the model is uncertain (entropy-aware).

Reported over five benchmarks with Qwen3-8B: +3.4% over GRPO, +6.3% over SDPO, up to 17.2% less compute per step. Read from the abstract only; a very recent preprint.

RL facts that matter here

On-policy, and the rollout/trainer mismatch

The maths assumes samples come from the policy being updated. Here two programs are involved: rollouts from llama.cpp (Q8_0 plus a GGUF LoRA) and training in bf16 PEFT in transformers. They define slightly different distributions. The release measured the quantisation part: Q8_0 against BF16 has a KL divergence of 0.0005 and the same top token 99.45% of the time.

Small, but the same kind of gap between other stacks (vLLM against FSDP) has been shown to make "on-policy" RL quietly off-policy (Yao, Liu et al., 2025, which proposes an importance-sampling fix; I couldn't read the full text).

  • Recompute log-probs in the trainer, not the server.
  • Take one update per rollout batch so the ratio clip rarely fires.
  • Log the mean server-vs-trainer log-prob gap as a canary. GSPO's sequence ratio tolerates this better.
  • Check how the thinking budget's forced end-of-thought is handled: those tokens weren't sampled and shouldn't carry loss.

Group size and informative groups

A group teaches only if it holds a right and a wrong answer. If a question's success chance is p, an 8-group is informative with probability 1 − p⁸ − (1−p)⁸.

p = 0.599%
p = 0.12566%
p = 0.157%
p = 0.0215%

A baseline "never" may be rare-but-possible, and larger groups reach further (Arctic-Text2SQL-R1 used 16 and saw no gain from 24 or 32). Eight matches the baseline's samples. Log the informative share: it is the run's real throughput.

Advantage normalisation

With one right answer in eight, GRPO's advantages are about +2.5 for the right one and −0.35 for each wrong one (the exact values depend on how std is computed). Without the std division (Dr. GRPO): +0.88 and −0.13. Dividing by std weights the hardest and easiest questions more; whether that helps or only adds variance is something the pilots can show.

KL to the SFT reference, free here

The reference is the policy with its RL adapter off: no second copy in memory, just an extra no-grad forward pass per training sequence. Published choices run from β = 0.04 (DeepSeekMath) to 0.001 (Arctic-Text2SQL-R1) to none (DAPO, MTIR-SQL). A small β is cheap insurance for a low-rank adapter and keeps the output format near SFT's.

Entropy collapse

RL tends to sharpen the next-token distribution until the model stops exploring (Cui et al., 2025). Signs: mean token entropy falling fast; a group's eight answers becoming near-identical, so the informative share drops; pass@1 up while pass@8 is flat or down. Defences: clip-higher, dynamic sampling, KL, a low learning rate, stopping early. Log distinct queries per group beside entropy.

Reward hacking in SQL and Cypher

The repo's rule is execution-only reward, and any sign of these is a finding.

  • DISTINCT everywhere. Passes when the check copies hold few duplicates. Canary: share of rollouts using DISTINCT.
  • SELECT * and extra columns. The strict match fails extra columns, but on gretel's one-to-three-table schemas * can equal the answer. Track columns returned.
  • Empty results matching empty references. A copy where the reference returns nothing (or only zeros and NULLs) proves nothing and isn't counted; the evalset drops such questions. Apply the same filter to training questions.
  • Format tricks. Several calls in a reply, no call, a call placed inside the thought. The parser's strictness is the defence.
  • Overfitting to the checker's copies. If a question's databases are identical on every visit, a query tuned to them can pass without being right. Fresh seeds per visit, and different copies for evaluation, test for it.
  • In run 2, the sandbox itself. Read-only connections, timeouts, row caps, no network, scratch copies. A model that can run ATTACH, PRAGMA or LOAD CSV has more to try.

Read the highest-reward and most-changed samples by hand each time; counters miss new tricks.

Undecided answers

Baseline scoring counts them neither way (148 of 1,600 answers, 97 of them text2cypher). In training it matters: counting them wrong punishes right answers on unverifiable questions, counting them right rewards anything. Options: remove them from the group, or drop questions with too few decided answers. About half of text2cypher's questions can't be decided at all.

Thinking length

The 1,024 budget stays capped, so thoughts can't grow forever, but they can pile up at the cap or shrink to nothing. Arctic-Text2SQL-R1 saw a U-shape (shorter, then longer as accuracy rose); SDPO's answers were ~3× shorter than GRPO's; Dr. GRPO's critique is that GRPO inflates wrong answers.

Canaries: median thought length, the share cut by the budget (1 of 1,600 baseline answers hit the token cap), thinking-off calls, the "can't answer, say so" rate.

LoRA for RL

LoRA Without Regret (Thinking Machines, Sept 2025) reports LoRA matching full fine-tuning in RL even at rank 1, which the authors argue is because policy gradients carry about one bit per episode, and recommends LoRA on all layers, MLP included. Their RL experiments were math-style on Llama and Qwen, not ours.

The SFT adapter is rank 16, alpha 32 on every linear layer. Reusing that keeps the GGUF conversion path proven, and a lower rank is an option.

Learning rate. They find the best LoRA rate is about 10× the full fine-tune rate. Full fine-tune RL papers use around 1e-6 (SDPO's feedback runs, GRPO's default in its comparison), which points to roughly 1e-5 here against SFT's 1e-4 on the same adapter. That is my reading, to be settled by the pilots.

Evaluation and noise

Since eight unchanged samples spanned 7 points, a method difference under ~4 points is noise on 198 questions. RL runs also vary by seed and a 16 GB run takes days, so each pilot will be one seed. Treat rankings between close methods as weak evidence.

On 16 GB

llama-server (~6 GB with 16 slots) and the trainer (~10-12 GB) can't both be resident, so each step is phases: generate and score; stop the server; train; convert the adapter; restart.

From the SFT run: GPU memory sat near 15.5 GB and the trainer crashed in WSL's GPU runtime; the fix was capping PyTorch at 80% of the card and tuning the allocator (the largest step needed 12.4 GB). Other risks:

  • System RAM pressure as weights move between RAM and GPU each step.
  • The checker's Neo4j and Docker on the same machine.
  • The Ctrl+C that ended the baseline's jobs twice (decision R3: start long jobs inside WSL, detached).
  • Run 2's longer sequences.
  • The need for a checkpoint/PAUSE protocol like SFT's.

On the Modal H100 fallback the same loop talks to vLLM instead of llama.cpp. No cost estimate exists yet, and any spend needs Rishi's OK.
