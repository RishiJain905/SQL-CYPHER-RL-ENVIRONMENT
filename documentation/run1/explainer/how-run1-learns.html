How Run 1 Learns

A 4-billion-parameter language model answers a question about a database by writing one query. A program runs that query. If the rows match the right answer, the model earns a point. Run 1 and run 1b repeat that loop thousands of times and nudge the model toward whatever earned points. This page draws the loop twice, once from the trainer's side and once from the model's, explains every number the run logs, and shows where in the code to turn each knob when a number goes wrong.

Words used on this page
Reinforcement learning (RL): training by trial and reward. The model tries, gets a score, and is nudged toward what scored.
SFT model: the starting model, first taught by example (supervised fine-tuning) to write queries. Training here never overwrites it.
LoRA: a small set of extra numbers added on top of the frozen starting model. Only it is trained; it is a 124 MB file.
Attempt (rollout): one complete try at one question: the thinking and the tool call.
Group: the 8 attempts at the same question. Training compares attempts within a group.
Checker: the program that runs an attempt's query on a real database and compares its rows with the reference query's rows.
Reward: +1 for a right answer, 0 for a wrong one, -0.1 for a malformed call, nothing when the answer cannot be judged.
Advantage: how much better than its own group's average an attempt scored, in units of the group's spread.
Token: the chunk of text a model reads and writes one at a time, roughly a word or a piece of a word.
Policy: the model as it behaves right now, with its LoRA.
KL divergence: how different two sets of next-token probabilities are, in nats.
Entropy: how undecided the model is about its next token.
Greedy / sampled: greedy always takes the likeliest token; sampling picks at random by the model's probabilities.
Evalset: 200 held-out questions the model never trains on, used to measure progress.
GRPO, SDPO, SRPO: the update rule. GRPO pushes attempts up or down by advantage, SDPO pulls a wrong attempt toward a teacher's probabilities, SRPO routes each attempt to one or the other.
Canary: a cheap number with a bound, watched so that a change in the model's habits is seen early.

Reading the group

Six attempts have a reward: one right (+1) and five wrong (0). The group mean is 1/6 = 0.167 and the spread is 0.373, so the right answer gets an advantage of +2.24 and each wrong one -0.45. The right attempt goes to the GRPO branch (push its tokens up). The five wrong ones each have a right sibling, so they go to the SDPO branch: a teacher that has been shown the right sibling's query tells the model which tokens it should have preferred. The two withheld attempts are left out of the update entirely.

Why was the third attempt withheld?

On the real biology graph (4,990 taxa, 13,706 relationships) exactly 1 taxon, the Sumatran Green Pigeon, is both Near Threatened and found in a cloud forest, and it has one relationship of each kind. So 1 path exists, and an answer with or without DISTINCT returns the same one row. The checker cannot tell them apart. CypherBench references use DISTINCT almost always, so a model that drops it is paid on this sparse graph and loses the habit. The probe stores every relationship twice: the same taxon then has 2 x 2 = 4 paths, the reference still returns 1 row, and an answer without DISTINCT returns 4. Section 3 tells the whole story.

2a. How far from the starting model

The model is trained by small changes to a patch (a LoRA: a small set of extra numbers added on top of the frozen starting model, so the starting model itself is never overwritten). The starting model is called the SFT model because it was first taught by example (supervised fine-tuning). Run 1 improved the model for about 19 steps and then drifted away from it while getting no better. These numbers say how far the patched model has moved, and whether the trainer is allowed to keep moving.

kl_sfthow far the model has moved from where it started, per tokensrc/sqlrl/run1/train_step.py:262
What it is

KL divergence, from scratch. At every position a language model gives each possible next token a probability. Two models, or one model before and after training, give two different sets of probabilities. KL divergence is a single number for how different the two sets are. Take the tokens the first model really writes, and average how much more probable the first model thought each one was than the second did, on a log scale. It is zero when the two agree. It grows when the first model starts favouring tokens that the second finds unlikely.

The unit is the nat, a natural-log unit. Turning a 50/50 choice into a certainty costs ln 2 = 0.69 nats.

What kl_sft measures here. The first model is the policy: the model as it behaves now, with its LoRA patch. The second is the SFT model, the same weights with the patch switched off. Before each update the trainer takes one attempt per question (32 attempts, about 10,000 tokens) and averages, token by token, log probability of the token under the policy minus log probability under the SFT model. That is KL(policy ‖ SFT) per token. The number does not say whether the change helped. It says how large the change is.

Per token, per answer. Answers are about 300 tokens, so the per-answer KL is about 300 times the number in the log. At 0.001 the policy rates its own answers a factor of e0.3 = 1.35 likelier than the SFT model would. At 0.03 that factor is e9, about 8,000. At 0.3 it is e90. Those are typical-answer ratios, not a probability of anything; they show how fast a small per-token number compounds.

What it tells us

How large the model's change from the starting model is, not whether the change helped. A small, steady rise while the evaluations improve is learning. A fast rise while they stall is drift: run 1 went from 0.115 to 0.294 in the nine steps after its best evaluation, with answers a quarter shorter and DISTINCT dropped.

Healthyabout 0.001 at step 10, 0.005-0.01 at step 20, then 0.03-0.05 around steps 28-32, and levelling off there (run 1b's expectation, run1b/RUNBOOK.md).

Where that lands-

A teaching toy: the 53% is real, the one-position framing is ours. In real answers the change is spread over many positions, and kl_sft adds them up.

Why it is measured from the server's side. The model that writes the attempts is the rollout server's: the SFT weights with the patch merged in and compressed to 8 bits. That is also the model that would ship, so its probabilities are the true ones. The trainer's own forward pass (in 16-bit arithmetic) rounds each layer's output after the patch's small addition is made, and for a small patch part of the addition is rounded away. So the trainer under-reads a young patch: the scatter chart above shows run 1 at 39% of the true value at 0.011, 64% at 0.046 and 98% at 0.294. The log therefore carries both: kl_sft (the server's probabilities minus the SFT model's, exact) and kl_sft_trainer (the trainer's view, for comparison).

It is noisy and has a floor. It is an average over 32 attempts. With no patch at all, at step 1, it still reads 0.0002 because the server's compressed weights are not bit-for-bit the trainer's. In run 1b step 4 it read 0.0028 between neighbours at 0.0002-0.0006. The step-to-step bumps below about 0.005 are measurement; read the trend.

kl_betathe strength of the pull back toward the starting modelsrc/sqlrl/run1/config.py:158
What it is

The KL penalty is an extra term in the training loss that pulls the model back toward the SFT model, like a leash. kl_beta is the leash's strength this step: the penalty is multiplied by it. A fixed strength would be a guess, so the code adjusts it each step from the drift just measured:

  • kl_sft above 0.045 (1.5 × the 0.03 target): the weight doubles, up to a ceiling of 6.4.
  • between 0.02 and 0.045: it stays.
  • below 0.02 (the target / 1.5): it halves, never below its start of 0.05.

This is PPO's adaptive penalty (Schulman et al., 2017) driven by the exact, server-side reading.

What it tells us

Whether the leash is slack or taut. At 0.05 it is barely felt. A weight that keeps doubling means the reward keeps pulling the model away harder than the leash pulls back.

Healthy0.05 until kl_sft passes 0.045, then doubling step by step until kl_sft stops rising; halving again when it falls under 0.02.
Actat its ceiling of 6.4 with kl_sft still above 0.045: the penalty cannot hold against the reward. Report it. (Run 1b has 0.05 in all 7 steps so far.)

What it is

The leash itself: the KL the penalty term actually computed in the update. It compares the whole next-token distributions of the patched and the unpatched model (the policy's 100 likeliest tokens plus one bucket for everything else), on every position of every trained answer, rather than only the one token that was sampled. So it carries no sampling noise, and its gradient always points back toward the SFT model.

Part 3

The ideas behind the numbers

Seven ideas that the numbers keep pointing at. Each one is explained from what it does in this run, with the run's own evidence.

Generalizationdoing well on questions the model has not been trained on

Generalization is performing well on new questions, not only on the ones practised. It happens when what the model learns is a skill (how to turn a question and a schema into a query) rather than a memory of particular answers. You cannot see it in training numbers, so the run checks it on a wall: training questions on one side, 200 held-out questions on the other.

Two protections make this stronger than usual. Every training question is used once, so the training solve rate is already a test on unseen questions. And CypherBench trains on 4 graphs (art, biology, soccer, terrorist attack) but is evaluated on 7 other graphs: a gain there is a gain on graphs the model never saw.

Overfittinglearning the practice set's quirks instead of the skill

Overfitting is the training score rising while the held-out score stays flat or falls: the model is memorising the practice material. It is not what run 1 showed. Its training solve rate never climbed, and after about step 19 the model kept moving without getting better anywhere. Three different patterns look alike in a single number; the table separates them by which of the numbers move.

Drift, and the leash that regularization puts on itkeeping a model near where it started

The SFT model is a good, general starting point (43.7% on a 1,000-question test set). The reward measures one thing. Moving a long way to improve that one thing can give away everything the reward does not see. Drift is distance from the starting model; kl_sft measures it.

Regularization is anything that holds a model back from fitting too hard. Here it is: the KL penalty (the leash: a loss term that grows with the distance from the SFT model), a small patch (a rank-16 LoRA cannot change the model arbitrarily), a low learning rate with a warm-up, a clip on how far any token's probability can move in one update, and never reusing a question. Run 1 had the last four and not the first; it drifted. Run 1b adds the penalty and halves the learning rate.

Narrowing (mode collapse)becoming consistent by giving up options

Reinforcement learning rewards what already works. Run long enough, the model concentrates on the answers it finds safest and stops exploring the rest: it narrows, which is also called mode collapse. A narrowed model looks better on mean@8 because it is consistent. It looks worse on pass@8, because the answers that were right only sometimes have disappeared.

The signature is three numbers moving together: mean@8 up, pass@8 down, entropy falling (and "sometimes" emptying into "never"). Run 1 showed part of this by step 25 (not the full pattern, since mean@8 did not rise): training entropy had fallen from 0.44 to 0.32, pass@8 went from 66.2 to 62.6 while mean@8 barely moved (40.8 to 39.7), and "never" rose from 66 to 74. The gate catches the significant case; entropy is how you see it first.

Reward hackingscoring more without getting better

Reward hacking is a model finding a way to earn reward that is not the thing the reward was meant to measure. Rewards here come only from execution: the answer must return the reference's rows. That blocks most tricks, but the checker can only judge on the data it has. Run 1 is the worked example.

  1. CypherBench references nearly always say DISTINCT, which removes repeated rows.
  2. The checker's CypherBench graphs are sparse. For 82% of those questions the reference returns the same rows without DISTINCT, so an answer without it passed.
  3. The model's use of DISTINCT on held-out answers fell from 22% to 9% over 28 steps, while the checker's right-rate on the questions whose reference uses it went up (36.6% to 40.6%). The score did not see the loss.
  4. On a denser graph such an answer returns each row several times: wrong. Part of what run 1 learned was a habit that fails in the real world.
  5. Run 1b's fix is a second, artificial database for passed CypherBench answers (the doubled graph) and no reward when the two disagree. Section 1b drew it.
Noisewhy one evaluation is good to about 3 points

200 questions is a small sample. One question moves a rate by 0.5 points, and the model also samples at random, so two measurements of the same model differ. The unchanged SFT model, measured again through the same pipeline, differed from its baseline by +1.3 greedy, -0.5 mean@8 and -2.7 pass@8. So a 2-3 point move on one evaluation is not a result.

What to do about it: compare question by question (the sign tests of 2e), look at several evaluations in a row instead of one, treat the training solve rate as a 5-step mean (a step swings by 0.1-0.2 with its batch), and keep the test set for a single final look.

Part 4

If you are the human in the loop

The run pauses itself on some rules and says nothing about the rest. This part is for the person who watches the numbers and decides what to change. Each situation lists the numbers that reveal it, the setting to change, the real line of code, which way to move it, and what it costs.

How a change takes effect

The one rule

Settings are read once, when the run process starts. The first time a run starts, the code writes its settings into the run's own config.json (the defaults, plus a preset such as run1b); every later start, including a resume, reads that file and nothing else. So editing the numbers in config.py changes the next new run, not the one that is going. To change a run that exists, stop it, edit its config.json, and resume.

  1. Look. The step's row in train_log.jsonl and the latest lines of events.jsonl say what the run did and why it paused.
  2. Stop cleanly. pause.py --run run1b --after-step writes a STOP file and the run ends after the current step. pause.py --run run1b frees the GPU at once and writes PAUSED; resuming redoes at most the cut step's update.
  3. Edit. Make a copy of config.json first (run 1 kept config.json.before-kl010 and others). Change the key. A key inside method_cfg or stop is changed inside that block.
  4. Resume with the command that started it (run.py --run run1b --preset run1b; the preset is ignored on a resume). The run clears STOP, STOPPED, PAUSED and FAILED when it starts, so a STOP meant for after an evaluation must be written after the restart.
  5. Ask first. Under the run books, changing any setting, a stop bound, the KL target or weight, the learning rate or the step count is the owner's decision, as is resuming after a stop rule, the gate or the turn rule paused the run.
Two things that do not work mid-run

Changing the dataset mix: a step's questions are positions in the pool (config.step_questions slices the next n of each dataset), so a new mix would reuse or skip questions. Make it a new run. And editing code (rewards, losses, the checker) while a run is going: the loss and the reward define what is being learned, so a change there is a new design with its own tests and a new run.
